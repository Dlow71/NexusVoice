## 🎯 系统定位

本RAG系统专为**Markdown技术文档**设计，核心特点：

- ✅ **保留原文**: 原始Markdown完整保存，便于溯源和展示
- ✅ **增强检索**: 翻译特殊节点（代码、表格、图片）提升检索效果
- ✅ **智能分割**: 基于语义结构和标题层级的智能分段
- ✅ **混合检索**: 向量检索 + 关键词检索 + RRF融合 + Rerank
- ✅ **异步处理**: 消息队列驱动，用户体验友好

## 💡 核心设计理念

### 1. 两阶段处理架构

**为什么需要两阶段？**

传统RAG系统通常只做一次处理：文档 → 切片 → 向量化。但对于技术文档（特别是Markdown），这种方式有明显缺陷：

| 问题 | 传统方案 | 本系统方案 |
|-----|---------|-----------|
| 代码块难以检索 | 直接向量化代码 | 翻译为自然语言描述 |
| 表格信息丢失 | Markdown表格直接向量化 | 转换为结构化文本 |
| 图片内容缺失 | 忽略图片或仅保存URL | GPT-4V OCR识别 |
| 原文不可溯源 | 原文被修改或丢失 | 原文完整保留 |

**两阶段设计**:

```
【阶段1】结构化解析与原文分割
    ↓
    目标: 保留原文，按语义结构分段
    输出: DocumentUnit表（原始Markdown段落）
    特点: 基于标题层级，保持文档结构完整性
    
【阶段2】翻译增强与智能分割
    ↓
    目标: 提升检索效果
    输出: PGVector（翻译后的向量片段）
    特点: 特殊节点翻译 + 长度控制 + 重叠分割
```

**关键原则**:
- ✅ **原文永不修改**: DocumentUnit.content 保持原样
- ✅ **翻译仅用于向量化**: 不保存翻译后的文本到关系数据库
- ✅ **故障隔离**: 阶段1成功后，阶段2失败可单独重试

### 2. 策略模式 + 工厂模式

不同文档格式（PDF/Markdown/TXT/WORD）使用不同的处理策略：

```java
// 工厂模式: 根据文件扩展名返回对应策略
DocumentProcessingStrategy strategy = 
    documentProcessingFactory.getDocumentStrategyHandler(fileExt);

// Markdown专属策略
@Service("markdown")
public class MarkdownRagDocumentProcessing 
    extends AbstractDocumentProcessingStrategy {
    
    // Markdown特有的两阶段处理逻辑
}
```

**优势**:
- 易于扩展新格式（如PPTX、Excel）
- 各格式处理逻辑独立
- 统一的处理接口

### 3. 异步消息驱动

使用RabbitMQ实现异步解耦：

```
用户上传
    ↓ 立即返回（响应<200ms）
保存文件 → 发送MQ消息(DOC_SYNC_OCR)
    ↓ 异步处理
文档解析 → 保存DocumentUnit → 发送MQ消息(DOC_SYNC_RAG)
    ↓ 异步向量化
向量化完成 → 更新状态 → 用户可查询
```

**优势**:
- 用户体验好：上传即返回
- 削峰填谷：应对高并发
- 支持重试：失败自动重试
- 可观测性：消息追踪和监控

### 4. 智能分割策略

**三层分割策略**，按优先级递减：

```
1. 段落级分割 (优先)
   - 分隔符: "\n\n"
   - 保持段落完整性
   - 适用场景: 段落长度适中的文档

2. 句子级分割 (备选)
   - 分隔符: "。！？.!?"
   - 保持句子完整性
   - 适用场景: 段落过长的文档

3. 强制截断 (兜底)
   - 固定长度截断
   - 保证不超过maxLength
   - 适用场景: 单句超长的情况
```

**重叠策略**:
- 每个片段与前一个片段重叠100字符
- 保持上下文连贯性
- 提升边界处的检索效果

## 🛠️ 技术栈选型

### 核心技术栈

| 类别 | 技术 | 版本 | 选型理由 |
|-----|------|------|---------|
| **后端框架** | Spring Boot | 3.x | 成熟的企业级框架 |
| **Markdown解析** | Flexmark | 0.64.x | 高性能AST解析器，支持扩展 |
| **向量数据库** | PGVector | - | PostgreSQL扩展，与关系数据库无缝集成 |
| **消息队列** | RabbitMQ | 3.x | 稳定可靠，支持死信队列和重试 |
| **Embedding** | text-embedding-3-small | - | 性价比高，1536维，效果好 |
| **LLM** | GPT-4 / Claude | - | 翻译和OCR |
| **对象存储** | MinIO / 阿里云OSS | - | 成本低，可扩展 |

### 为什么选择PGVector？

| 对比项 | PGVector | Pinecone | Milvus |
|-------|----------|----------|--------|
| **部署复杂度** | ⭐ 简单（PG扩展） | ⭐⭐⭐ 需云服务 | ⭐⭐ 需独立部署 |
| **数据一致性** | ⭐⭐⭐ ACID事务 | ⭐ 最终一致 | ⭐⭐ 可配置 |
| **成本** | ⭐⭐⭐ 开源免费 | ⭐ 按量付费 | ⭐⭐ 开源但资源消耗高 |
| **查询性能** | ⭐⭐ 中等 | ⭐⭐⭐ 高 | ⭐⭐⭐ 高 |
| **适用场景** | 中小规模 | 大规模云端 | 大规模本地 |

**结论**: 对于企业内部RAG系统，PGVector是最优选择。

## 🚀 快速开始

### 1. 系统要求

- **Java**: JDK 17+
- **PostgreSQL**: 15+ (带PGVector扩展)
- **RabbitMQ**: 3.x
- **Redis**: 可选，用于缓存
- **对象存储**: MinIO或云OSS

### 2. 核心依赖

```xml
<dependencies>
    <!-- Flexmark Markdown解析 -->
    <dependency>
        <groupId>com.vladsch.flexmark</groupId>
        <artifactId>flexmark-all</artifactId>
        <version>0.64.8</version>
    </dependency>
    
    <!-- LangChain4j -->
    <dependency>
        <groupId>dev.langchain4j</groupId>
        <artifactId>langchain4j</artifactId>
        <version>0.35.0</version>
    </dependency>
    
    <dependency>
        <groupId>dev.langchain4j</groupId>
        <artifactId>langchain4j-pgvector</artifactId>
        <version>0.35.0</version>
    </dependency>
    
    <!-- RabbitMQ -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-amqp</artifactId>
    </dependency>
</dependencies>
```

### 3. 5分钟快速体验

```bash
# 1. 启动PostgreSQL + PGVector
docker run -d --name postgres \
  -e POSTGRES_PASSWORD=password \
  -p 5432:5432 \
  pgvector/pgvector:pg15

# 2. 启动RabbitMQ
docker run -d --name rabbitmq \
  -p 5672:5672 -p 15672:15672 \
  rabbitmq:3-management

# 3. 配置application.yml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/agentx
    username: postgres
    password: password

# 4. 启动应用
./mvnw spring-boot:run

# 5. 上传测试文档
curl -X POST http://localhost:8080/api/rag/upload \
  -F "file=@test.md" \
  -F "datasetId=test-dataset"

# 6. 查询测试
curl -X POST http://localhost:8080/api/rag/search \
  -H "Content-Type: application/json" \
  -d '{"question": "系统架构是什么？", "datasetId": "test-dataset"}'
```

### 与传统RAG的对比

| 特性 | 传统RAG | 本系统 |
|-----|---------|--------|
| **原文保留** | ❌ 通常丢失 | ✅ 完整保留 |

- 技术文档知识库

- 纯文本文档（两阶段处理可能过度）

## 🤝 常见问题

### Q1: 为什么不直接用langchain的TextSplitter？

**A**: langchain的TextSplitter是通用方案，对Markdown的特殊节点（代码、表格）处理不够精细。我们的两阶段架构可以：
- 保留原始Markdown结构
- 针对性翻译特殊节点
- 基于语义而非固定长度分割

### Q2: 翻译特殊节点会增加多少成本？

**A**: 
- 代码块和表格约占文档20%
- 翻译成本约为embedding成本的5倍
- 但检索准确率提升15-20%
- 总成本增加约3倍，但ROI很高

### Q3: 可以不用PGVector吗？

**A**: 可以，但不推荐。PGVector的优势：
- 与PostgreSQL无缝集成，减少技术栈复杂度
- ACID事务保证数据一致性
- 部署和运维成本低
- 对于大多数企业场景性能足够

### Q4: 支持其他文档格式吗？

**A**: 支持！项目采用策略模式，已实现：
- ✅ Markdown (最完善)
- ✅ PDF (基于GPT-4V OCR)
- ✅ TXT (基本支持)
- ✅ WORD (基本支持)

扩展新格式只需实现`DocumentProcessingStrategy`接口。
